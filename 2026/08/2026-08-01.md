## 1. 推理服务相关学术论文

### Ranking Before Serving: Low-Latency LLM Serving via Pairwise Learning-to-Rank

- 论文链接: https://arxiv.org/abs/2510.03243
- 发表时间: 2025年10月（ISC High Performance 2026 收录）
- 来源: ISC High Performance 2026 Research Paper Proceedings (第41届国际会议, 德国汉堡)

**论文总结:**

本文关注 LLM 推理服务中的请求调度问题。在多用户共享 GPU 的推理场景下，请求的执行顺序直接影响整体延迟分布和用户体验。现有调度器大多使用 FIFO 或简单的长度估算排序，难以准确预测请求的实际执行时间，导致尾部延迟恶化。

论文提出将请求排序建模为成对学习排序（Pairwise Learning-to-Rank）问题：通过学习请求特征对（prompt 长度、解码历史、模型状态等）之间的相对执行时间关系，训练一个排序模型来决定请求的服务顺序。相比回归预测绝对执行时间，成对排序对特征噪声更鲁棒，且优化目标直接对齐延迟排序而非绝对值精度。

实验在 NVIDIA A100 上使用 Llama-2-7B 进行评估，该方法在多种工作负载下显著降低了 p95/p99 尾部延迟，同时保持了高吞吐量。

**亮点:** 将推理调度的「预测执行时间」重新定义为「排序请求优先级」，用排名学习替代回归预测，降低了模型对特征噪声的敏感度。

## 2. KV Cache 复用相关学术论文

### CacheTune: Adaptive KV Cache Reuse for Fast Long-Context LLM Serving

- 论文链接: https://arxiv.org/abs/2605.24022
- 发表时间: 2026年5月

**论文总结:**

长上下文推理中，TTFT（Time-to-First-Token）延迟是首要瓶颈。传统前缀缓存仅适用于严格前缀场景；非前缀 KV cache 直接复用会破坏跨块全局注意力关系，导致生成质量显著下降。当可复用的 KV cache 被卸载到 GPU 外部缓存池时，跨异构硬件层的 I/O 开销又成为新的 TTFT 瓶颈。

CacheTune 提出了一个频率引导、硬件感知的非前缀 KV cache 复用系统。核心方法分两层：

1. 语义层：通过频域分析离线识别对跨注意力恢复最关键的 KV 对，在线仅选择性重计算这些语义关键 token，其余 KV 直接复用。
2. 系统层：结合稀疏 KV 传输、多流异步重叠、延迟位置编码恢复、以及硬件感知的自适应重计算比率调优，在异构缓存池间平衡计算与数据移动。

实验显示，CacheTune 在主流 LLM 和长上下文任务上实现 3.72x-4.86x TTFT 加速和 3.93x-6.21x 吞吐量提升，生成质量接近全量重计算。即使缓存卸载到 I/O 受限的 SSD/HDD 存储，仍能保持 2.34x-2.36x TTFT 加速。

**亮点:** 首次将非前缀 KV cache 复用的语义恢复与计算-I/O 协同优化统一到同一系统，频域分析识别关键 token 的思路新颖。

## 3. 推理 Infra 相关学术论文

### AMPD: Efficient Multi-round LLM Inference over Disaggregated Serving

- 论文链接: https://arxiv.org/abs/2602.14516
- 发表时间: 2026年2月

**论文总结:**

随着 LLM 工作流从单轮问答演进到多轮 Agent 和迭代 RAG，prefill-decode（PD）分离架构面临新挑战：多轮推理中增量 prefill 任务与 decode 任务交替出现，现有分离系统未能自适应地调度这些交错的工作负载，导致 SLO 达标率低下。

AMPD 提出了面向多轮 LLM 推理的分离式服务框架。核心设计：

1. 自适应增量 prefill 调度：根据实时负载动态决定增量 prefill 在 prefill 实例还是 decode 实例上执行，以及如何调度，以最大化 SLO 达标率。
2. 专用规划算法：为多轮场景定制资源分配和并行策略规划，推导 prefill 和 decode 两阶段的最优配置。

实验在 Llama3.1-70B 上使用 ToolBench、GAIA、HotpotQA、DuReader 等多轮工作负负载评估，AMPD 相比 NVIDIA Dynamo 等 SOTA 基线显著提升 SLO 达标率，同时保持较低的端到端延迟。

**亮点:** 首次系统性地解决多轮 Agent 工作流下 PD 分离架构的增量 prefill 调度问题，指出现有分离系统对多轮场景的「一刀切」prefill 路由是性能瓶颈根源。

## 5. Vibe Coding Nice Practice

### LLM 友好文档 + 全栈调试可见性：给 AI 编码工具正确的地基

来源: OpenSaaS.sh 2026年实践总结 (https://docs.opensaas.sh/blog/2026-03-16-best-way-to-vibe-code-saas-2026)

**问题:** Vibe coding 在原型阶段极快，但随复杂度增长迅速触顶。AI 原生平台（Replit、Lovable、Bolt）生成的代码与平台基础设施耦合，15-20+ 组件后出现严重的上下文退化——代码重复、模式遗忘、不一致。开发者反馈在 Bolt.new 上仅调试 AI 生成的 bug 就花了 1000+ 美元 token 费用。

**实践:**

1. 用本地 AI 编码工具（Claude Code / Cursor / Codex）替代 AI 原生平台，保持对代码和架构的完全控制。
2. 两个关键技术配合使用：
   - LLM 友好文档：在项目根目录放 `llms.txt`，把框架文档转为 AI 可直接消费的格式。技巧：在文档站 URL 后加 `.md` 获取 LLM 友好版本（如 Stripe 的订阅指南），直接传给 Agent 让它准确实现集成。
   - 全栈调试可见性：在后台运行 `wasp start`，让 Claude Code 实时看到服务器日志和报错；配合 Chrome DevTools MCP 实现浏览器端调试闭环。
3. 搭配成熟的 SaaS 样板（如 Open SaaS）作为起点，给 AI 一个结构化的地基，而非从零生成。

**核心原则:** Vibe coding 的成败不取决于 AI 工具本身，而取决于你给 AI 工具的地基——结构化代码库 + 可消费文档 + 调试反馈闭环。
