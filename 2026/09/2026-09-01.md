Characterization of Request and Token Energy Costs for LLM Inference Workloads on GPU Platforms
论文链接: https://arxiv.org/abs/2608.28044
发布时间: 2026-08-28
类别: cs.PF 性能分析（已被 IISWC 2026 录用）
论文总结: LLM 推理按 token 计价而 GPU 能耗按推理窗口消耗，这一错配使 token 归一化指标并不完整：平均 token 能耗下降时，单请求总能耗可能反升。论文提出分解式能耗模型（一次性 prefill 与生成启动成本加每步边际能耗），在 H100/H200 上对 dense 与 MoE 模型刻画两类能耗随批次、上下文与输出长度的变化：输出从 10 增至 512 token 时 token 能耗降十倍但总能耗升五倍，批处理收益受上下文长度约束，MoE 低并发时固定能耗偏高。能量感知服务应联合优化请求能耗与 token 能耗。
亮点: 用可分解的能耗模型揭示 token 能耗指标的盲区，为能量感知调度给出实测依据。

五、Vibe Coding 的 Nice Practice
实践: 用三层提示结构替代一句话需求，让 AI 一次生成接近生产质量的代码
问题描述: 对 AI 编码助手说"帮我做个登录页"这类模糊指令，产出的往往是通用 demo 代码：技术栈不对、缺错误处理、安全考虑缺失，需要反复来回修改才能用。根因是 AI 默认按训练数据中最常见的"快乐路径"生成，边界情况与安全措施在训练数据中出现频率低，不主动要求就不会有。
具体做法: 按 Supabase 总结的三层结构组织提示词。第一层技术上下文与约束：指明框架、语言、样式方案与架构模式（如 React + TypeScript + Tailwind）；第二层功能需求与用户故事：从用户视角描述具体行为与交互；第三层集成要求与边界情况：说明与现有代码的对接方式、空输入、加载态、并发点击、快捷键等真实场景。生成后进入迭代循环：先追问"这段代码可能出什么问题、要处理哪些边界情况"，再问"应遵循哪些安全实践、如何处理敏感数据"，最后让 AI 自审"假设明天就上线，找出安全隐患、性能瓶颈与缺失的错误处理"。配合数据建模、API 端点、UI 组件三类模板，可显著减少往返修改。
来源链接: https://supabase.com/blog/vibe-coding-best-practices-for-prompting
